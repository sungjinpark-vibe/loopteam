# QA 시나리오 — 이름 하나로 후반부 상태에 바로 들어가기

**대상 독자: 이 코드베이스를 처음 보는 QA 에이전트/사람.** 사전 지식이 필요 없습니다.
이 문서에 적힌 URL과 콘솔 호출 두 개가 전부입니다.

## 왜 있는가

5인 전문가 플레이테스트 3회 동안 **건물 융합, 월말 정산, 만원(滿員) 마을의 공원 이연**은 한 번도
끝까지 구동되지 않았습니다. 기능이 고장나서가 아니라, 앱을 처음 잡은 사람이 손으로
Lv.5 쌍둥이 건물 두 채를 만들거나 한 달을 넘기거나 81칸을 채울 방법이 없었기 때문입니다.
그 결과 **정상 동작하는 기능에서 약 50점이 깎였습니다.** 이 시나리오들은 그 접근 불가 상태를
한 단계로 열어 줍니다.

## 어떻게 부르는가

### 방법 1 — URL (권장, 이것만 알면 됨)

```
http://localhost:5173/?scenario=<이름>
```

로드되면 앱이 그 시나리오를 저장소에 쓰고, **그 시나리오가 전제하는 날짜로 시계를 고정한 뒤**,
`?scenario=`를 URL에서 떼고 다시 부팅합니다. 페이지가 안정되면 바로 그 상태입니다.

### 방법 2 — 콘솔 (이미 열려 있는 탭에서)

```js
window.__aitLoadFixture("fusion-ready");   // 위 URL과 완전히 같은 경로. 알아서 리로드함
```

### 시계 조작 (월 넘김 · 다음날 아침)

```js
window.__aitSetTimeTravelDate("2026-08-01");  // 즉시 반영
location.reload();                            // ← 이 리로드가 핵심
window.__aitGetTimeTravelDate();              // 현재 고정된 날짜 확인, 없으면 null
window.__aitSetTimeTravelDate(null);          // 실제 기기 날짜로 복귀
```

> **리로드를 반드시 같이 하세요.** 월말 정산(F16)과 대기열 소진(F14)은 **부팅 때 딱 한 번**
> 돌아갑니다(`useTownStore.ts`의 부팅 이펙트). 날짜만 바꾸고 리로드하지 않으면 헤더 숫자만
> 바뀌고 정산도 소진도 일어나지 않습니다. 고정된 날짜는 `sessionStorage`에 남아
> 리로드 뒤에도 유지됩니다(탭 단위, 브라우저 세션 종료 시 소멸).

전부 **개발 빌드 전용**입니다. 프로덕션 번들에는 들어가지 않으며 `npm run gate:extra`가 이를 검사합니다.

## 시나리오 목록

| 이름 | 부팅 직후 상태 | 여기서 무엇을 확인하나 |
|---|---|---|
| `fusion-ready` | 건물 5채, 시계 2026-08-10 | 융합 2단계 확인 + 취소 2경로 |
| `fusion-ready-lv6` | 건물 7채, 시계 2026-08-10 | Lv.6 + Lv.6 → Lv.7, 등급 혼합 금지(F5) |
| `month-end` | 건물 42채, 시계 **2026-07-31** | 월 넘김 정산 + 기념비 |
| `full-town` | 건물 **80채(지도 만원)**, 시계 2026-08-10 | 만원 마을의 공원 이연 |

| `capExceeded` | 건물 10채 + 대기 3개, 시계 2026-08-02 | 다음날 아침 소진 + 씨앗 1회 지급 |

### `fusion-ready`

```
http://localhost:5173/?scenario=fusion-ready
```

**들어 있는 것** — 식비 1×1 Lv.5 두 채(합칠 수 있는 유일한 쌍), 그리고 **조건별 미끼 1채씩**:

| 미끼 | 위반 조건 |
|---|---|
| 식비 **2×1** Lv.5 | F3 — 풋프린트 불일치 |
| **카페** 1×1 Lv.5 | F2 — 카테고리 불일치 |
| 식비 1×1 **Lv.4** | F1 — 최대 레벨 아님 |

미끼가 있으므로 "행복 경로가 된다"가 아니라 **"조건이 실제로 강제된다"**를 증명할 수 있습니다.
융합 픽 모드에서 반짝이는 후보는 **정확히 1채**여야 합니다.

**조작 순서**

1. 건물 탭 → 상세 시트에 **융합하기** 버튼이 보임
2. 융합하기 → 픽 모드(하단 "융합할 건물을 선택하세요"). 후보 1채만 강조
3. 후보 탭 → 확인 다이얼로그 "건물을 융합할까요?" (**취소 / 합치기**)
4. 합치기 → 상대 건물 칸이 비고, 생존 건물 상세 시트가 **Lv.6**

**취소 경로 2개** (둘 다 마을을 그대로 두어야 함)
- 픽 모드 하단 바의 **취소**
- 확인 다이얼로그의 **취소**

### `fusion-ready-lv6`

`fusion-ready`와 같고 **이미 Lv.6인 식비 1×1 두 채**(`fuse: 1`)가 추가됩니다.
Lv.6을 초기자로 잡으면 후보는 **다른 Lv.6 한 채뿐**입니다 — 옆에 나란히 있는 Lv.5들은
F5(같은 fuse 등급끼리만) 때문에 절대 후보가 되지 않습니다. 합치면 **Lv.7**.

### `month-end`

```
http://localhost:5173/?scenario=month-end
```

시계가 **2026-07-31 — 그 달의 마지막 날, 아직 열려 있는 달**에 고정됩니다.
`unsettledPeriods`는 현재 달을 제외하므로 **여기 머무는 동안에는 아무것도 정산되지 않습니다**(정상).

월말 정산과 기념비를 보려면 **달을 넘기세요**:

```js
window.__aitSetTimeTravelDate("2026-08-01");
location.reload();
```

리로드 직후 2026-07이 정산되고 **기념비 1기**가 지도에 새겨집니다(무늬가 다른 오벨리스크,
`aria-label`이 "기념비…"). 기념비를 탭하면 그 달의 요약이 나옵니다.
이것이 패널이 3회 동안 한 번도 시뮬레이션하지 못한 **월 롤오버**입니다.

### `full-town`

```
http://localhost:5173/?scenario=full-town
```

RX1-N2 배치 규칙이 허용하는 **실제 최대치까지 지도를 채웁니다(현재 80채)**. 숫자는 하드코딩이
아니라 `placeNew`가 거절할 때까지 채워서 얻습니다 — 배치 규칙이 바뀌면 이 시나리오도 따라갑니다.

오늘 슬롯은 손대지 않았으므로 **다음 기록/무지출 청구가 "자리가 없어서" 이연되는 경로**를
그대로 볼 수 있습니다. `오늘 무지출!` 을 누르면 공원이 지어지지 않고
`오늘은 무지출! 공원은 내일 아침에 지어드릴게요 (대기 1개)` 토스트가 뜨며 헤더에
`내일 지을 건물 1개 대기 중`이 붙습니다.

> **알려진 한계(결함 후보, `evidence-scenarios/findings.json` 참조)**: 지도가 계속 만원이면
> 다음날 아침으로 넘겨도 그 공원은 지어지지 못하고 같은 약속 문구가 매일 반복됩니다.
> 재현: 위 청구 후 `__aitSetTimeTravelDate("2026-08-11"); location.reload();`

### `no-spend-ready`

```
http://localhost:5173/?scenario=no-spend-ready
```

시계 2026-08-10, **오늘 날짜의 지출이 0건**(지출은 전부 08-09/08-08). 슬롯도 자리도 남아 있어
`오늘 무지출!` 알약이 **즉시 눌러집니다**. 누르면 공원이 바로 서고 알약이 사라집니다
(`full-town`의 이연 경로와 대조군).

`canClaimNoSpend`는 **오늘 날짜의 지출이 한 건이라도 있으면** 거절합니다 — 다른 시나리오에서
알약이 안 보인다면 대개 그 이유입니다.

### `fresh`

```
http://localhost:5173/?scenario=fresh
```

유일하게 `onboarded: false`로 기록되는 시나리오 — 그래서 **S1 온보딩이 실제로 렌더됩니다.**
(`empty` 픽스처는 항상 온보딩 완료 상태로 기록되므로 이 용도로 쓸 수 없습니다.)
카드의 **건너뛰기**를 누르면 예산을 쓰지 않은 채 마을 화면으로 들어가고
`첫 지출을 기록하면 첫 건물이 생겨요` 빈 상태가 보입니다.

### `capExceeded` — 다음날 아침 소진

```
http://localhost:5173/?scenario=capExceeded
```

시계 2026-08-02, 하루 상한(10)을 다 쓴 뒤 **3건이 대기열에** 있습니다. 다음날 아침으로 넘기면:

```js
window.__aitSetTimeTravelDate("2026-08-03");
location.reload();
```

대기 3건이 건물로 소진됩니다(10채 → 13채). **씨앗 지급이 한 번만 일어나는지**는 같은 날짜로
한 번 더 리로드해서 확인합니다 — `localStorage["ait.v1.economy"]`의 `seeds`와
`grantedEventKeys`가 그대로여야 합니다(실측: 34 → 34, 키 4개 동일).

## 증거

전 시나리오를 위 호출만으로 끝까지 구동한 스크린샷·수치: `docs/qa/evidence-scenarios/`
(`capture.mjs`가 재실행 가능한 하네스, `findings.json`이 측정값).

## 시나리오를 추가하려면

`src/devtools/fixtures.ts`의 `FIXTURES`에 `Fixture`를 하나 더 등록하면 끝입니다 —
URL 경로와 콘솔 경로가 같은 레지스트리를 읽으므로 배선할 곳이 따로 없습니다.
`fixtures.test.ts`가 모든 항목의 **결정성(두 번 만들어 바이트 동일)**을 자동으로 검사합니다.
