## §1 — 검증된 현재 상태: F9는 이미 있다

평가단의 "경로가 아예 없다"는 **부재가 아니라 발견성 실패**다. 전 경로가 살아 있고 도달 가능하다:

| 조각 | 위치 |
|---|---|
| 행 탭 → 시트 | `components/HistoryScreen.tsx:109-143` (`.history-row`는 `<button>`, `onClick={() => onOpenRow(e)}`), `:190` `openRow`, `:316-323` 시트 마운트 |
| 수정·삭제 시트 | `components/EntryDetailSheet.tsx:56` (`onSave`/`onDelete`), 삭제 확인 `ConfirmDialog` `:206-214` |
| 순수 로직 | `historyActions.ts:84` `deleteEntryEffects`, `:154` `editEntryEffects` |
| 스토어 배선 | `useTownStore.ts:1452` `deleteEntry`, `:1496` `updateEntry` |
| 기존 테스트 | `useTownStore.history.test.tsx`, `historyActions.test.ts`, `components/EntryDetailSheet.test.tsx` |

**`.history-row`에 탭 가능하다는 시각적 단서가 하나도 없다** — 셰브론도, 눌림 상태도, 안내 문구도 없다. 평가단이 못 찾은 이유이자 §7이 고치는 것.

이미 올바르게 회수되는 것 (건드리지 말 것): 건물 제거, grow 기여분 EXP 백아웃(0 하한), F14 큐 자재 드롭, 저축 금액 백아웃, 금액 수정 시 EXP 티어 차액(`historyActions.ts:195-212` — `expGainFor` 신·구 델타).

## §2 — 실제 결함: 씨앗은 지급되고 회수되지 않는다

`historyActions.ts` 전체에 `economy`·`seed`·`award` 참조가 **0건**이다. `deleteEntry`/`updateEntry` 어느 쪽도 `applyAward`의 역연산을 호출하지 않는다.

기록 1건이 지급하는 씨앗 (`useTownStore.ts:955-981`, `economy/awards.ts:88-113`):

| award | key | 금액 |
|---|---|---|
| `entry` | `seed:entry:<entryId>` | `BALANCE.seedAwards.entry[rung]` = `[2,4,6,8,10]` |
| `build` | `seed:build:<buildingId>` | `BALANCE.seedAwards.build[rung]`, 기록이 건물을 **세웠을 때만** |
| `streak` | `seed:streak:<date>` | `min(2×streakDays, 20)` |
| `tier` | `seed:tier:<tier>` | 티어 교차 시 |

**착취 A (삭제 파밍)**: 150,000원 기록 저장 → `entry` 10 + `build` 상단 rung 수령 → 삭제 → 건물·EXP는 사라지지만 **씨앗은 남는다**. 기록 id가 매번 새로 발급되므로 `grantedEventKeys` 멱등성이 막지 못한다. 반복 시 씨앗 무제한.

**착취 B (금액 하향 수정)**: 150,000원으로 저장해 최상단 rung 씨앗 수령 → 100원으로 수정. EXP는 `historyActions.ts:198`이 정확히 되돌리지만 **씨앗은 그대로**. 상단 rung과 하단 rung의 차액이 순이익.

Gate-3 5차가 `entry` 보상을 금액 연동 테이블로 바꾸면서(`balance.approved.ts:114`) 착취 A의 1회 수익이 커졌다 — 이 결함은 최근에 악화된 쪽이다.

### §2.1 불변식 (INV-12.1) — 이 문서 전체의 축

> 살아 있는 기록 E에 대해 실제로 지급된 씨앗은 **항상**
> `awardFor({ kind:"entry", entryId:E.id, expGain: expGainFor(E.amountKrw, tiers) }).amount` 와 같다.
> E가 건물 B를 세웠다면 `seed:build:<B.id>` 도 같은 rung으로 지급된 금액과 같다.

- **수정**은 차액을 정산해 불변식을 유지한다.
- **삭제**는 불변식이 보장하는 그 금액을 정확히 회수한다 — 그래서 회수는 저장된 기록 필드만으로 **재계산**할 수 있고, `LedgerEntry`에 `seedsGranted` 같은 필드를 새로 만들 필요가 없다 (기존 `expGainFor` 재계산 방식과 동일한 규율).

## §3 — 회수 규칙

### §3.1 삭제

| 대상 | 규칙 |
|---|---|
| `entry` 씨앗 | `seed:entry:<id>` 가 `grantedEventKeys`에 있으면 그 금액 회수, 키 제거. 없으면 (미지급/링버퍼 이탈) **회수 안 함** |
| `build` 씨앗 | 삭제로 건물이 제거되는 경우에만 `seed:build:<buildingId>` 동일 처리 |
| 건물 | 기존 동작 유지 — 세운 건물 제거, grow 기여분은 호스트 EXP에서 백아웃(0 하한) |
| 큐 자재 | 기존 동작 유지 (F14) |
| 저축 | 기존 동작 유지 (`adjustSavings` 음수) |
| `pendingGrowChoice` | **신규**: 그 기록을 가리키고 있으면 함께 해제 (기존 `dropFromQueue`와 같은 취급 — 지금은 누락돼 죽은 기록을 가리키는 선택지가 남는다) |
| 스트릭·슬롯·티어 | 회수 안 함 (§6) |

키가 링버퍼(`GRANTED_EVENT_KEYS_CAP` = 64)에서 밀려난 경우 회수하지 않는 것은 착취 구멍이 아니다: 키를 밀어내려면 그 사이에 64건의 다른 이벤트가 필요하고, 그 이벤트들은 각자 정당하게 지급된 것이라 "밀어내기"가 파밍보다 비싸다. 반대 방향(지급 안 된 키를 회수)이 실제 손해이므로 보수적으로 이쪽을 택한다.

### §3.2 수정 (금액/타입)

금액이 바뀌면 rung이 바뀔 수 있다. 지급된 키마다:

```
delta = awardFor(신 금액).amount − awardFor(구 금액).amount
```

- `delta > 0` → 추가 지급 (키는 이미 있으므로 `applyAward`의 멱등 검사를 우회하는 전용 정산 경로 사용).
- `delta < 0` → 회수, 0 하한 + 부족분 `seedDebt`.
- `delta === 0` → 아무것도 쓰지 않는다 (동일 rung).

EXP·건물·저축 차액은 **이미 올바르므로 손대지 않는다** (`historyActions.ts:195-212`).

스트릭·10채/일 카운트는 **소급 변경하지 않는다** — 그날 기록하는 행위 자체는 실제로 있었다 (HQ 가드레일, 기존 D-10과 동일 논리).

### §3.3 잔액 부족 — `seedDebt`

회수액 > 현재 잔액이면 잔액을 0으로 두고 부족분을 이월한다. 없으면 착취 C가 열린다: 씨앗을 모아 SKU를 사서 소진한 뒤 기록을 전부 삭제 → 회수가 0에서 잘려 **SKU가 공짜**가 되고, 반복 가능.

`EconomyState`에 선택 필드 하나 (`exp`/`fuse`/`w`/`h`가 이미 세운 *absent === 0* 규율, 마이그레이션 없음, 구 JSON 그대로 파싱):

```ts
  seedDebt?: number;   // 미회수 잔액; absent === 0
```

- 회수: `debt += max(0, amount − seeds)`, `seeds = max(0, seeds − amount)`.
- 적립: `applyAward`가 **먼저 빚을 상계**하고 남은 만큼만 잔액에 더한다.
- 구매한 SKU는 절대 회수하지 않는다 (`ownedSkus` 영구 — PM-DECISIONS §F-ECON, ADDENDUM-03 DE-9 rule 4). 빚이 그 자리를 대신한다.
- 표시: 별도 UI를 만들지 않는다. 삭제 확인 다이얼로그가 그 순간에만 사실대로 알린다 (§7).

## §4 — 범위: 당월만

`deleteEntry`/`updateEntry`는 현재 **로드된 아무 달이나** 수정한다 (`useTownStore.ts:1455-1459`, `entriesForMonth(prev, ym, todayYm)`). HistoryScreen은 지난달로 자유롭게 이동할 수 있으므로 지난달 기록도 지금 수정·삭제된다.

지난달은 불변이다:

- F16 정산은 `monumentSummary`를 **기념비 건물에 값으로 박아** 저장한다. 지난달 기록을 고치면 기념비가 말하는 숫자와 그 달 내역이 어긋난다 — 역사가 자기 자신과 모순된다.
- 기념비 재배열 금지 원칙과 같은 논리: 새겨진 것은 다시 쓰지 않는다.

**규칙**: `ym !== today.slice(0,7)` 이면 수정·삭제 전부 거부. 판정은 **스토어에서** 한다 (신뢰 경계) — UI 숨김은 안내일 뿐 방어가 아니다.

`occurredOn` 수정도 당월 안에 머물러야 한다: 당월 밖으로 날짜를 옮기면 기록이 정산된 달로 흘러들어가 같은 모순을 만든다. `EntryDetailSheet`의 날짜 필드는 상한 `today`(기존)에 더해 **하한을 당월 1일**로 잠근다.

## §5 — 융합 체인: 삭제 불가

가장 어려운 경우다. `fusionActions.ts`의 검증된 사실:

- `applyFusion`은 생존 건물의 `exp`를 **그대로 두고** `fuse`만 +1 한다. 소멸 건물은 통째로 삭제되고 **그 EXP는 어디에도 합산되지 않는다**.
- `remapEntryBuildingRefs`는 소멸 건물을 가리키던 **모든 기록의 `buildingId`를 생존자로 갈아끼운다** (ADDENDUM-11 §5.4).

그래서 융합 후에는 두 종류의 기록이 같은 생존자를 가리킨다:

| 기록 | 생존자 EXP에 기여했나 | 지금 삭제하면 |
|---|---|---|
| 생존자 자신의 창건·성장 기록 | 예 | 창건 기록 삭제 시 **융합 타워가 통째로 사라진다** (두 건물분 진척 소멸) |
| 소멸 건물에서 갈아끼워진 기록 | **아니오** — 그 EXP는 융합 때 이미 버려졌다 | 생존자에게서 **준 적 없는 EXP를 빼앗는다**. `fuse`는 그대로라 겉보기 레벨이 조용히 내려간다 |

두 경우 모두 파괴적이고, 갈아끼워진 기록과 원래 기록을 **사후에 구별할 데이터가 없다** (`buildingId`만 남고 출처 기록이 없다).

**결정 (D-12.4) — 삭제 불가 처리, 파괴 범위 최소화.**

판정식 한 줄이 두 경우를 모두 잡는다:

```
융합에 얽힘 ⟺ (entry.buildingId 가 가리키는 건물 b 가 존재하고 fuseOf(b) > 0)
             또는 (buildingForEntry(buildings, entry.id) 가 fuseOf > 0 인 건물)
```

- **삭제 불가**, **금액·타입 수정 불가** (금액 수정도 같은 EXP 경로를 타므로 같은 손상을 낸다).
- **메모·카테고리·날짜 수정은 허용** — 경제·EXP를 건드리지 않는다. 오타 정정이라는 원래 목적은 이 경로로 남는다.
- 사유를 UI에 명시한다 (§7).

### §5.1 검토했으나 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 체인 해체 (융합을 되돌리고 소멸 건물 복원) | 소멸 건물의 `exp`·`plotIndex`·`variantIndex`가 보존되지 않는다. 복원하려면 융합 시점에 스냅샷을 저장해야 하고, 그건 되돌리기 위한 새 영속 구조 — 오입력 정정 하나를 위해 지불하기엔 과하다. 게다가 빈 자리가 이미 다른 건물에 점유됐을 수 있다 |
| EXP만 빼고 건물은 유지 | 갈아끼워진 기록에 대해선 **없던 EXP를 빼는** 것이라 애초에 틀렸다. `fuse`와 `levelOf`가 어긋나 Lv.10이 조용히 Lv.8이 된다 |
| 기록에 "EXP 기여 여부" 필드 추가 | 이미 융합된 저장본에는 소급 적용할 수 없다 (그 정보는 이미 소실). 신규 저장본만 고쳐지는 반쪽 규칙 |

삭제 불가는 **당월 + 미융합**이라는 좁은 창을 남기지만, 융합 조건 자체가 Lv.5 두 채를 요구하므로(ADDENDUM-11 §2.2) 갓 기록한 당월 오입력이 이미 융합에 얽혀 있을 확률은 낮다. 오입력 정정이라는 목적은 실질적으로 보존된다.

## §6 — 회수하지 않는 것 (명시)

| 항목 | 이유 |
|---|---|
| `streakDays` / `lastActOn` / `longestStreakDays` | 그날 기록한 행위 자체는 있었다. 소급 취소는 "실수 한 번에 연속 기록이 끊긴다"는 더 나쁜 경험 |
| `slotsUsedToday` (10채/일) | 기존 D-10 유지 — 삭제해도 슬롯은 환불되지 않는다. 환불하면 슬롯 상한이 무의미해진다 |
| `highestTierSeen` / `seed:tier:*` | 설계상 단조 증가(한 번 본 티어는 되돌리지 않는다). 티어 씨앗은 마을 규모가 실제로 그 지점을 지났을 때 한 번 지급된 것 |
| `ownedSkus` (구매물) | "건물을 지워도 구매는 취소되지 않는다"는 기존 선례 (`useTownStore.ts:1161`). 대신 `seedDebt`가 정산한다 |
| F16 기념비 / `monumentSummary` | 지난달 산물이며 §4에 의해 애초에 수정 대상이 아니다 |
| 캐시충전 스텁 | 무관·불변 |

## §7 — UI

1. **발견성 (평가단 지적의 실제 원인)**: `.history-row` 우측에 셰브론 어포던스 + 눌림 상태. 새 컴포넌트 없이 `App.css`의 기존 BEM식 클래스로.
2. **당월 아님**: 시트의 저장·삭제 버튼 `disabled`, 사유 문구 — *"지난달 기록은 정산이 끝나 수정할 수 없어요."*
3. **융합에 얽힘**: 삭제 버튼·금액/타입 필드 `disabled`, 사유 문구 — *"이 기록은 합쳐진 건물에 들어가 있어 금액 수정·삭제를 할 수 없어요. 메모와 분류는 바꿀 수 있어요."*
4. **삭제 확인**: 기존 `ConfirmDialog` 유지, 설명문에 회수량을 사실대로. 예 — *"함께 지어진 건물이 사라지고, 씨앗 8개를 돌려받아요."* 잔액이 부족하면 *"지금 씨앗이 부족해서 다음 적립에서 차감돼요."*
5. **날짜 필드**: 하한 당월 1일, 상한 `today` (§4).

TDS `BottomSheet`/`ConfirmDialog`/`Button` 관례와 기존 `EntryFields` 재사용 — 새 폼 컴포넌트를 만들지 않는다.

## §8 — 원자성

기록·경제·건물이 서로 다른 청크에 산다: 기록은 `entries.<ym>`, 건물은 `builtOn` 월 청크, 경제는 `ait.v1.economy`. 기존 규율(ADDENDUM-11 §3.1)을 그대로 따른다 — **트랜잭션을 만들지 않고, 앞으로 완주하는 순서 + 부팅 시 전진 수복**.

삭제 쓰기 순서 (역순 실패가 손해를 내지 않는 순서):

1. **경제 먼저** — 씨앗 회수 + 키 제거를 저장. 여기서 중단되면 사용자는 씨앗만 잃고 기록은 남는다 (되돌릴 수 있는 상태, 착취 아님).
2. **건물 청크** — 건물 제거 또는 호스트 EXP 백아웃.
3. **기록 청크** — 기록 제거 + `core`(town: 큐·저축·`pendingGrowChoice`).

역순(기록 먼저)이면 중단 시 **기록은 사라졌는데 씨앗은 남는다** = 착취 A가 그대로 재현된다. 그래서 경제가 먼저다. 새 pending 필드는 필요 없다 — 이 순서에서 부분 실패는 전부 "사용자에게 불리하되 정합성은 유지" 쪽으로만 떨어진다.

수정도 같은 순서 (경제 → 건물 → 기록).

## §9 — 스토어 계약 (UI와 로직의 접점)

```ts
export interface EntryMutability {
  canEdit: boolean;        // 어떤 필드든 수정 가능한가
  canEditAmount: boolean;  // 금액·타입(경제에 영향) 수정 가능한가
  canDelete: boolean;
  reason: null | "past-month" | "fused";
}

// 스토어가 노출; UI는 문구를, 스토어 액션은 방어를 위해 같은 함수를 읽는다
entryMutability(entry: LedgerEntry, ym: string): EntryMutability

// 삭제 확인 다이얼로그의 정직한 문구용
seedClawbackPreview(entry: LedgerEntry): { seeds: number; shortfall: number }
```

- `past-month` → `{ canEdit:false, canEditAmount:false, canDelete:false }`
- `fused` → `{ canEdit:true, canEditAmount:false, canDelete:false }`
- 그 외 → 전부 `true`, `reason:null`

`deleteEntry`/`updateEntry`는 **호출 첫 줄에서 이 함수로 자기검사**하고 거부한다. UI 비활성화는 안내이지 방어가 아니다.
