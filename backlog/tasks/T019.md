## What happened
The first Gate 3 run for app_in_toss (5-expert playtest, `playtest.js`) came back **avg 64.4/100,
every single expert below the 80 floor** (60/67/70/72/53). This is not a marginal miss — it's a
genuine, substantive failure that surfaces real gaps `state/PROGRESS.md` had been claiming were
closed. **This is being reported as unfinished, per VISION.md §5** — the MVP is not actually
complete despite every individual T001-T018 task having cleared its own gate.

## Root cause of the false "MVP complete" record
`docs/spec/MVP-SPEC.md` §12's build order has **step 5**: F16 (monthly settlement + 기념비), S1
(onboarding), F17 (memo chips), polish/empty-dense-error states. **No task was ever opened for step
5.** The backlog jumped from step-4 items (T012/T013/T014) straight to "MVP feature-complete" without
anyone verifying step 5 landed. Confirmed by direct grep: `useTownStore.ts` has zero `monument`
references (F16 dead), no `Onboarding` component existed pre-Gate-3 (S1 never built), and
`backlog/tasks/T013.md`'s own brief assumed "budget is presumably only settable at onboarding right
now (F11, already built)" — an assumption nobody ever checked. This is exactly the failure mode the
whole gate system exists to catch, except it happened at the PM's own scope-tracking level, not an
individual task's.

## Real findings (not exhaustive — full panel report has 5x this detail, see `state/journal.md`)
1. **Reward is decoupled from money entirely.** `decideBuildOrQueue` never receives `amountKrw` — a
   ₩1 entry and a ₩10,000,000 entry produce an identical building. A no-spend day (the one pro-saving
   act in the loop) yields 1 building AND burns a slot — a tenth the growth of ten impulse buys same day.
2. **Overspending has zero mechanical consequence.** Mood is a text string only; nothing decays, greys
   out, or is lost. The town only ever goes up — no tension, nothing at stake.
3. **No onboarding (S1).** Confirmed missing in code prior to Gate 3. Cold start shows game-economy
   jargon ("남은 건축 슬롯 10/10") with zero explanation, for an explicitly non-gamer-first audience.
4. **F16 (monthly settlement + monuments) is not built**, despite being the spec's own named answer to
   "make month 12 different from month 1" and despite prior records claiming it was done.
5. **Tier-celebration is a hard blocking modal** that swallows the primary "add another entry" action —
   friction in a ledger whose core promise is fast logging.
6. Two identical console errors fire on every single page load (TDS provider's safe-area-inset bridge).
7. Several flows **could not be verified at all**: no exposed TimeTravel UI hook for QA to test a
   controlled +1-day rollover, no true concurrent-mash test, tier-celebration idempotency under a
   multi-threshold fixture jump.

## Separate: an engine-tooling bug, found and fixed, no data loss
`playtest.js`'s post-fix-round mechanical gate check was hardcoded to `gate.ps1` (Unity) with no
override — the exact gap `quality-loop.js` already had fixed for this project. The round's own
automatic "Fix" step ran for real (see below) but then the verification step failed with "not a Unity
project," triggering a "repair the compile error" prompt built on a false premise. **The safety
classifier correctly blocked that repair agent** before it could act on the false premise (risk: it
might have tried to restructure the React codebase into Unity shape). No files were touched by the
blocked call. Fixed at the engine level: `playtest.js` now accepts `args.gateScript`/`args.runHint`
overrides (mirroring `quality-loop.js`), and `gate/gate-node.ps1` gained the `-SkipTest` switch
`playtest.js`'s fix-round verification always passes. Committed: engine `5e1b269`.

## Why this is `blocked`, not something the PM pushed through alone
This goes past bug-fixing into scope and design-priority territory that needs the director's judgment:
- **F16/F17 were explicitly on the spec's own "cut if time runs out" list** (MVP-SPEC.md §12: "If time
  runs out, cut in this order: F17 → F16 → F13 → F15 → F12") — the director may be fine leaving these
  cut permanently rather than building them now. That's his call, not an inference.
- **S1 onboarding was NOT on that cut list** — i.e., the spec itself treated it as essential, unlike
  F16/F17. Worth flagging that distinction plainly.
- **The reward/money-decoupling and overspend-has-no-consequence findings are core-loop design
  questions**, not bugs — fixing them means changing what "a building" actually represents, which is a
  product decision, not an implementation detail.
- Given the scope (multiple weeks-original spec's own step 5, plus real design gaps the panel found
  beyond that), this needs a prioritized plan, not five more autonomous fix-forward rounds at once.
