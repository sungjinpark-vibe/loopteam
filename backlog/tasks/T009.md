## Brief
Implement **part (a)** of `app_in_toss/docs/spec/ADDENDUM-02-placement-and-move.md` — random initial
placement + the boot-time self-healing reconciler. This is data-only (no UI), independently
demoable ("buildings now land randomly instead of in fixed order"), and carries all of this
feature's real risk per the addendum's own build-order note (§8.2): **"(a) is independently
shippable and carries all the risk; (b) carries all the interaction fiddliness."**

**Part (b) — long-press move + UI — is a separate follow-up task, not this one.** Do not implement
move/drag/long-press here.

Read directly: §3 (Random initial placement — §3.1 concepts, §3.2 `openPlotCount`, §3.3
`pickPlot`/`allocatePlots`, §3.4 growth/gap answer, §3.5 call-site diff, §3.6 `reconcilePlacement`),

AC is directly contradicted and retired, replaced per §6.1), §7 (compatibility diff against the real
T002-T007 code — read it, the addendum's own per-file verdict table in §7.2 is a good checklist),
§7.4 (the ADDENDUM-01 evidence rule this retires and its replacement — do not just delete the rule,
replace it as specified).

**Key design point, do not deviate**: `openPlotCount`/pool sizing provably guarantees `freePlots(...).length >= 1`
at every town size — this is what makes the later move feature never dead-ended. Get this right; it's
the foundation the follow-up task depends on.

**`rng() = 0` must reproduce the exact pre-change sequential town** (0, 1, 2, …) on a fresh town —
this is the compatibility bridge that keeps existing fixtures/tests meaningful (§3.3's AC-P7).
