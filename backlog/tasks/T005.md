## Brief
Director feedback via Discord (2026-08-03, msg 1533630433005146142), verbatim:
> 1. 예적금, 주식 투자에 대한 건물도 만들어줘.

This changes two things the approved spec (`app_in_toss/docs/spec/MVP-SPEC.md`) currently decides
differently — write a **spec addendum** (a new doc, do not edit MVP-SPEC.md itself, which is
implementer-off-limits and PM-merge-only per the T002 incident) proposing how to reconcile both:

**1. Savings sub-type buildings.** Current spec (F13, §5) has ONE generic 저축탑 (savings tower) —
저축 entries explicitly place no building and consume no slot, specifically to keep the daily-cap
invariant from ever rationing how much a user may save (§5 F13's own rationale: "the app must never
say you saved too much today"). The director now wants distinct buildings for at least 예적금 (time
deposit/installment savings) and 주식 투자 (stock investment) specifically. Design how to satisfy this
**without breaking F13's core invariant** (저축 must still never be capped or slotted — re-linking
savings to the daily build-slot economy would reintroduce the exact inverted-incentive problem F13
exists to solve, see spec §1.3). The likely direction: split 저축 into sub-categories (예적금, 주식
투자, and whatever else 저축 already covers — check `content.placeholder.ts`/`types.ts` from T002 for
the current category set) each rendering its OWN building/structure that grows with that sub-type's
cumulative amount, still outside the slot/cap system — effectively multiple F13-style towers instead
of one. Propose the concrete data model change (category set, what drives each structure's growth
tier) and exactly what changes vs. what F13 already has.

**2. Road-based town layout.** Current spec (F3/S2, §5/§6) is a plain scrolling tile grid
(`TOWN_COLUMNS = 6`, serpentine fill, CSS-grid + SVG — MVP deliberately avoids canvas/isometric
rendering per §5 WON'T list, "removes an entire class of risk"). The director wants a more
village-like feel: roads, with buildings placed near/along them, similar to Fortune City's actual
layout. Design a **CSS-grid-compatible** road layout — do not propose isometric/canvas rendering,
that WON'T-list decision stands unless you argue explicitly for overturning it (and if you do, flag
it loudly as a scope/engineering-cost change for the director, don't just assume it). A plausible
direction: road tiles interspersed in the grid (e.g. a road row/column pattern) with building plots
adjacent, still addressable via a `plotFromIndex`-style pure function so T002's existing placement
logic isn't rewritten wholesale — but you are the designer here, propose what actually reads as a
village, not just the easiest patch.

Read directly: `app_in_toss/docs/spec/MVP-SPEC.md` §5 (F2, F3, F13), §6 (S2), §8 (data model), §13
(D-2 category set, D-13 savingsTowerSegments — both now potentially superseded by your proposal).
Read the current implementation too — `app_in_toss/src/{types,selectors,content.placeholder}.ts` and
`src/components/{TownGrid,PlaceholderBuilding}.tsx` — so your proposal is grounded in what actually
exists, not just the spec text.
