## Brief
Director feedback via Discord (2026-08-04), verbatim:
> 건물 위치는 유저가 선택할수 있도록 해줘. 최초 건물을 세울땐, 랜덤 위치 건설이고, 그 이후엔 건설된
> 건물을 롱탭해서 옮길수 있도록

Translation, confirmed with the director: (1) when a building is first constructed, it lands at a
**random** valid plot (not the current sequential/systematic fill order), (2) after that, the player
can **long-press an existing building and move it** to a different valid plot.

This **reverses a PM engineering default** (D-31 in `app_in_toss/docs/spec/ADDENDUM-01-savings-and-roads.md`,
which shipped automatic/systematic placement, reasoned from the app's ≤3-tap entry-speed budget).
Write a spec addendum (new doc, `ADDENDUM-02-...`, do not edit `MVP-SPEC.md` or `ADDENDUM-01` — both
are implementer-off-limits, PM-merge-only) that redesigns placement. This is a real architecture
change, not a cosmetic one:

**What currently exists** (read before designing — `app_in_toss/src/`):
- `selectors.ts`: `plotFromIndex(i)` — pure, storage-order → screen coordinate. `Building.plotIndex`
  is **monotonic, assigned once via `town.nextPlotIndex++`, and MVP-SPEC's F2 explicitly says
  "nothing ever reflows"** once placed.
- `townLayout.ts` (from T006, ADDENDUM-01 §3): `cellFromIndex`, the road/block layout, the frontage
  invariant (every plot cell has a road neighbour), `SERPENTINE_COLUMNS` (screen-adjacency mapping).
- `entryActions.ts`: on save, `applyNewEntry` creates one `Building` at the next sequential plot
  (or queues it if no slots — F14).
- The savings block (T006's `SavingsRow.tsx` + the fixed head-of-street cells) is structurally
  separate from the normal plot-index space — **this feature should NOT need to touch it.**

**What the addendum must design, concretely:**
1. **Random initial placement**: instead of `nextPlotIndex++` (strictly sequential), pick a random
   *available* plot index/cell within whatever the town's current frontier is. Define exactly what
   "available" means (e.g. any index up to some frontier bound, or any index whose cell doesn't
   collide with an already-occupied one) and what happens to town size/growth pacing — does the town
   still grow by exactly one plot-worth of frontier per build, or can it now leave gaps that never
   fill? Both are valid designs; pick one and justify it against F3's "readable picture of your
   spending" goal (a town full of permanent gaps reads differently than a dense one).
2. **Move via long-press**: a `moveBuilding(buildingId, toPlotIndex)` (or equivalent) operation —
   define validity rules (can't move onto an occupied plot, must the destination still satisfy the
   frontage invariant, can you move a building onto ground the town hasn't "grown into" yet or only
   within already-placed bounds), the UI interaction (long-press → some kind of placement mode →
   tap destination → confirm), and exactly what persists (this is a real change to `plotIndex`, which
   F10's persistence design and F2's AC currently assume is write-once).
3. **What does NOT change**: the daily build-slot cap (F4), the queue (F14), the frontage invariant
   itself (a moved building must still end up on a valid, road-adjacent plot), the savings block. Say
   so explicitly for each.
4. **Compatibility**: diff against T002-T007's actual shipped code (read it, don't guess) — same
   discipline as ADDENDUM-01's break tables (`§5` there is a good model to follow). A town saved
   before this change has buildings at their old sequential positions; does anything need to migrate,
   or does it just work going forward?
5. **Scope discipline**: this is a placement/movement feature, not a rethink of everything else. Do
   not redesign F1-F17 wholesale. If you find a genuine new open decision only the director can make
   (there will likely be at least one — e.g. whether the frontier concept applies at all, whether
   moving costs anything), surface it plainly, do not guess.

**Process note, learned the expensive way on ADDENDUM-01**: keep this tighter in scope than that one
was. ADDENDUM-01 took 6 rounds and ~1.5M+ tokens partly because of scope growth across rounds — this
feature is narrower (placement mechanics, not a whole new building category), so aim to get it right
in 1-2 rounds by being concrete and checking real code up front, not iterating scope after the fact.
