## Brief
Implement MVP-SPEC.md §5 F12 — JSON export/import, the last remaining MVP feature. T013 already
added stub rows for 내보내기/가져오기 in the settings sheet (`SettingsSheet.tsx`) — wire them to
real logic here, don't restructure the sheet.

**F12 · JSON export / import**: 설정 sheet's **내보내기** serializes the entire state (all
month-chunked entry/building chunks + the core: town, budget, onboarded, schemaVersion) to a single
downloadable `.json`. **가져오기** accepts one such file and replaces state after an explicit
destructive-action confirm, validating `schemaVersion`. Rejected imports (unknown schema version,
malformed JSON) change nothing.
**Why this is a Must, not a nice-to-have** (per the spec): it's the only way a demo state moves
between machines, it makes the "no server yet" decision reversible, and it's the sole mitigation for
local-only storage.
**AC**: export → wipe the browser profile (or open in a fresh context) → import → byte-identical
state, including plot indices, the materials queue, streak, and the savings towers/structures.
Importing a file with an unknown `schemaVersion` shows an error and leaves the existing state
untouched. Malformed JSON is rejected the same way, not a crash.

**Read the existing storage code before writing anything new** — `storage.ts`'s chunked read/write
API, `schemaVersion`/`LAYOUT_VERSION` handling from earlier tasks (T006's `LAYOUT_VERSION` migration
notice is a relevant precedent for "load old/foreign state safely"), and `devtools/fixtures.ts`'s
`loadFixtureIntoStorage` for the pattern of writing a full state blob through the chunked API in one
pass (export/import is structurally the same operation, just to/from a downloaded file instead of a
fixture object).

**Toss mini-app constraint**: this is a WebView/browser context, not a native app — "download a file"
and "pick a file to import" both go through standard browser APIs (`<a download>` + Blob for export,
`<input type="file">` for import), not any native file-system SDK. Confirm this actually works in a
real browser before assuming a Toss-specific API is needed — it almost certainly isn't for this
feature.

## Acceptance criteria
- [ ] Export produces a single downloadable `.json` containing every chunk (all months' entries and
      buildings) plus the core (town, budget, onboarded, schemaVersion) — verified by actually
      downloading and inspecting the file in a browser
- [ ] Import accepts that file, shows a destructive-action confirm before replacing state, and
      results in byte-identical state after import (plot indices, queue, streak, savings
      towers/structures all preserved) — verified live: export → clear storage → import → compare
- [ ] Import of a file with an unknown/missing `schemaVersion` is rejected with a visible error;
      existing state is provably untouched (not partially overwritten)
- [ ] Import of malformed/non-JSON input is rejected the same way, no crash
- [ ] `npm run build` succeeds, `tsc --noEmit` clean, ALL existing tests still pass, gate green
      (`gate/gate-node.ps1`)
- [ ] No regression: `docs/spec/` untouched, nothing outside `app_in_toss/` modified, S2/기록/settings/
      move feature all still work
