## Brief
T015 passed 90/100 but its team-lead review flagged a third, unfixed instance of the nested-confirm
backdrop-lockup bug in `EntrySheet.tsx` (S4, primary add-transaction flow). A fix-forward round
(commit `da5d291`) wired the shared hook into that site and was sent for verification — **it scored
86/100, FAIL** (bar 90). Real findings, not nitpicks:

1. **C2 −5, a real race condition**: `useConfirmDialogBackdropFix.ts` assumes exactly one
   `[aria-label="닫기"]` node exists at a time ("verified live" — was true for the original two sites,
   false for EntrySheet: 2 nodes while the nested confirm is open). The fix only works today because
   TDS's confirm dimmer happens to unmount within one `requestAnimationFrame`. On a slow device or a
   heavy commit — precisely the condition that produces the original vendor bug — it could walk the
   wrong subtree and silently no-op.
2. **C2 −4**: zero tests bind the hook to `EntrySheet` — deleting the one wired line would still pass
   413/413. The exact class of miss this round exists to fix is not caught by the suite.
3. **C5 −3**: `npm test` (the command the gate actually runs) is nondeterministic at HEAD — 3
   failures across ~16 runs at `useTownStore.history.test.tsx:250` (`ensureMonthLoaded` asserted
   synchronously without awaiting the load, line 249). The `--no-file-parallelism` workaround used to
   get a clean run was never committed. Not caused by `da5d291`, but it means the gate itself can't be
   trusted to catch a real regression.
4. **C1 −2**: `useConfirmDialogBackdropFix.test.tsx`'s docblock still says "for both EntryDetailSheet
   and SettingsSheet" — stale, now three call sites.
